## 0. 两个必须先分清的结论

**结论 A：`sdk/benchmark/generic/provenance/` 不是文档溯源，是"实验可复现性清单"。**
它记录的是 *某次 benchmark 运行用了哪个 commit / 哪版 prompt / 哪套工具 schema*，与"这句话出自哪个文件第几页"毫无关系。详见 §4.1。真正的文档溯源机制在 citation 链路（§4.2），藏在 `cite_index` 这个名字下。

**结论 B：溯源能力比目录结构看起来强得多，但粒度卡在"文件级 + 块级"。**
`conversation_source_search_t` 是一张真正的"回答↔来源"持久化表，带 `unit_id`（回答片段级）外键。页号/坐标在 ES 里**已经存下来了**，但在工具组包时被 `SearchResultTextMessage` 的字段集**丢弃**。这是一个字段扩展问题，不是重建问题。

**ID 生成不稳定（溯源隐患）**：`_preprocess_documents()` `:719-722`：
```python

        """Convert SearchResult object to dictionary format to save all data."""
        return {"title": self.title, "url": self.url, "text": self.text, "published_date": self.published_date,

                "score_details": self.score_details, "cite_index": self.cite_index, "search_type": self.search_type,
                "tool_sign": self.tool_sign}

        index = f"{self.tool_sign}{self.cite_index}"
```

## 7. 一句话行动建议

1. **溯源不用重造**：扩 `SearchResultTextMessage` 字段（page_number / chunk_index / coordinates / es_doc_id）+ 改稳定 chunk ID + 打开 `ENABLE_CITATION_CLICK_HIGHLIGHT` → 页级/块级溯源即可落地，工作量集中在一条竖切（SDK dataclass → `run.py` 缓冲 → ORM → 迁移 → 前端）。
2. **知识图谱必须全自研**：图存储 + 实体/关系抽取 + 多跳检索算子，Nexent 侧零基础；标签体系（`TagDefinition`/`ResourceTagAssignment`）是唯一可复用的本体工程骨架。
3. **解析链路的两个开关**：`strategy="fast"` 关掉了 OCR 与表格结构化；`model_type == "multi_embedding"` 关掉了图片提取。若赛题涉及扫描件/表格/图片，需先打开这两个开关或换解析器。
