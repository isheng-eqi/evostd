# 六维资产标识：字段定义、来源判据与错填对照

六维覆盖现行判据库全部 12 条可编译条款。**任何一维空着，资产卡就是不合格的。**

## 总表

| 维 | 字段 | 类型 | 把关条款类型 | 取值来源 |
|---|---|---|---|---|
| **D1 身份维** | `asset_id` | str | 格式约束 | `asset_ingest` 生成，不由人填 |
| | `cited_standards` | list[str] | 跨文档引用（白名单） | 文件里实际引用的标准编号 |
| **D2 形态维** | `modality` | enum | 受控词表 | 三模态识别结论，取值 ∈ {文本, 表格, 图文, 影像} |
| | `annotation_note` | str | 条件必填 | 图文/影像模态时必填 |
| **D3 权限维** | `secrecy` | enum | 受控词表 | 取值 ∈ {公开, 内部, 秘密}，取自文件密级标识或用户指定 |
| | `declassify_date` | str | 条件必填 | `secrecy == 秘密` 时必填 |
| **D4 归属维** | `owner_dept` | str | 必填约束 | 责任部门，取自文件或用户指定 |
| | `storage_uri` | str | 必填约束 | 实际存放位置 |
| **D5 时序维** | `collect_time` | str | 跨字段一致性 | 采集时间，`≤ ingest_time` |
| | `ingest_time` | str | 跨字段一致性 | 入库时间 |
| **D6 质量维** | `quality_score` | number | 数值范围 | 0 ~ 100 |
| | `completeness` | number | 数值范围 | 0 ~ 1 |
| | `file_hash` | str | 格式约束 | 64 位小写十六进制 |

## D1 身份维

**在管什么**：这条资产是谁、它依据什么标准。

| 字段 | 规则 | 错填对照 |
|---|---|---|
| `asset_id` | 8~64 位字母/数字/连字符，全局唯一 | ❌ `短`、❌ `AST_2026_0001`（下划线不合法）、❌ 手写一个看起来像的编号 |
| `cited_standards` | 每一项都必须存在于受控标准清单中 | ❌ `GB/T 99999-2099`（清单外）、❌ 把标准名当编号填 |

**注意方向**：`cited_standards` 走的是**白名单**语义——「必须存在于清单中」。
所以清单漏了一项会导致合规资产被误判违规。遇到这种情况，
是**清单需要补**，转 `clause-proposal`，不要改资产。

## D2 形态维

**在管什么**：这条资产以什么形态承载信息。

- 只支持三模态：**文本 / 表格 / 图文**。视频与纯图表本版不覆盖，明确告知用户。
- 受控词表里有四个取值（含 `影像`），`图文` 与 `影像` 不同：
  - `图文` = 图像 + 说明文字共同表意（如质检照片配说明）
  - `影像` = 影像类资产本体（如整段影像记录）
- **`annotation_note` 的触发条件**：模态为 `影像`（或按当前判据库声明的触发值）时必填。
  填之前先看 `std_clause_list` 里该条款的 `when_value`，**不要按印象判断**。

| 错填 | 后果 |
|---|---|
| `modality = "表格图像"` | 词表外取值，直接违例 |
| 图文模态没写 `annotation_note` | 条件必填违例，且下游无法解释这张图在说什么 |
| 把 PDF 一律归为 `文本` | PDF 含表时应归 `表格`，判据按模态分流 |

## D3 权限维

**在管什么**：谁能看、什么时候可以解密。

- `secrecy` 三选一：`公开` / `内部` / `秘密`。**不要发明第四级**。
- `declassify_date`：`secrecy == 秘密` 时必填，格式与 `collect_time` 保持一致。
- 密级判定依据必须记入资产卡（文件密级标识 / 用户指定），因为它直接决定是否需要 `declassify_date`。

| 错填 | 后果 |
|---|---|
| `secrecy = "机密"` | 词表外取值（词表里是 `秘密`），直接违例 |
| 秘密级但 `declassify_date` 留空 | 条件必填违例 |
| 为省事把一切都标 `公开` | 绕过判据但造成实际泄露风险，属人为规避，不是合规 |

## D4 归属维

**在管什么**：谁负责、放在哪。

- `owner_dept`：责任部门名称。**空字符串、全空格、空数组都算未填**。
- `storage_uri`：实际存放位置，要能被下游解析（`oss://...` / `file://...` 等）。

| 错填 | 后果 |
|---|---|
| `owner_dept = "  "` | 必填判据把纯空白视为未填，仍然违例 |
| `storage_uri` 写「本地磁盘」 | 无法被下游寻址，等于没登记 |

## D5 时序维

**在管什么**：采集与入库的先后关系。

- 要求 `collect_time <= ingest_time`。
- 两个字段任一缺失或为 `None` 时该判据**放行**，所以缺时间字段不会被这条判据抓到——
  要靠你自己的缺口清单发现。
- 日期格式写成可比较的 ISO 形式（`YYYY-MM-DD`）。格式不可比对时，
  脚本会标为「无法机械比较」，此时**不得**当作通过。

| 错填 | 后果 |
|---|---|
| `collect_time` 晚于 `ingest_time` | 一致性违例。**先问哪个才是对的**，不要默认改后者 |
| 两个时间字段格式不一致（一个带时间一个不带） | 可能比较结果错误，先统一格式 |

## D6 质量维

**在管什么**：这条资产的质量与完整性可被量化。

| 字段 | 区间 / 格式 | 错填对照 |
|---|---|---|
| `quality_score` | 0 ~ 100 的数值 | ❌ `130`、❌ `"87.5分"`（带单位）、❌ 用 0~1 的分数填 |
| `completeness` | 0 ~ 1 的小数 | ❌ `1.8`、❌ `93`（把百分数填进来了） |
| `file_hash` | 64 位小写十六进制 | ❌ 大写、❌ 被截断、❌ 用 MD5（32 位）冒充 |

**最容易混的一对**：`quality_score` 是百分制，`completeness` 是 0~1。填反了会同时产生两条违例。

## 硬锚点自查的四个检查面

用 `std_hard_anchors` 取锚点后，按下表逐面核对。锚点覆盖率越高，人的工作量越小。

| 检查面 | 锚点长什么样 | 自查动作 |
|---|---|---|
| 受控词表 | 一份取值清单 | `modality` / `secrecy` 逐字比对，**大小写与全半角都要一致** |
| 取值域 | 一个区间 | `quality_score` / `completeness` 落在区间内 |
| 必填清单 | 一串必填字段名 | 逐字段检查非空（含纯空白） |
| 格式样例 | 一个正则或一个示例值 | `asset_id` / `file_hash` 与示例同形 |

**锚点取不到时不要猜值。** 该条款类型还没有机械锚点，说明它需要人工确认——
把它记成待确认项，转 `clause-proposal` 补锚点。
