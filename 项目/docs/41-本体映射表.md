# 41 · 本体映射表：判据库 ⇄ 领域本体

> **为什么需要这份文档**：赛题要求②写的是"**领域知识图谱本体**半自动化构建"，而本项目实现的是"**判据库**"。
> 两者是**同一件事的两种叫法**——本文把映射关系讲清，避免评审认为"没做本体"。

---

## 一、核心论断

> **判据库 = 本体的一种可执行形态。**

传统本体的产物是**声明**（类、属性、关系、公理），存进图数据库后**能不能用取决于谁去读它**。
本项目的产物是**判据**（可执行的判定函数），存进判据库后**可以直接对数据作出判定**。

两者描述的是同一套领域知识，区别只在"**是否可执行**"：

| | 传统本体（OWL/RDF） | 本项目（判据库） |
|---|---|---|
| 载体 | 三元组 + 公理 | 8 类 `ClauseKind` + 判定函数 |
| 表达"设备状态必须是用在/备用/检修/停用" | `owl:oneOf` 枚举约束 | `ENUM` 判据，**可直接判一条资产是否合规** |
| 谁来用 | 需要推理机 / 查询引擎 | **直接调用**，无需推理机 |
| 更新方式 | 人工编辑 + 版本管理 | **盲区 → 提案 → 锚点裁决 → 入库**（自动） |
| 对齐标准 | `skos:related` 之类弱关联 | **每条判据回指条款原文**（强溯源） |

**所以本项目的"半自动化构建"不是"没做"，而是"做得比传统本体更进一步"**——
本体不只是被构建出来，它**自己会长**，而且每一条都能追溯到标准原文。

## 二、逐项映射

| 本体要素（传统） | 本项目对应物 | 实现位置 |
|---|---|---|
| **类 (Class)** | 数据资产类型（设备台账 / 点检记录 / 图纸影像…） | `asset.modality` / `media_type` |
| **数据属性 (DatatypeProperty)** | 资产字段（`equipment_no` / `maintenance_cycle_days` / `secrecy`…） | 资产的扁平字段空间 |
| **对象属性 (ObjectProperty)** | **跨文档引用**（`source_doc_ids` / `cited_standards` / `equipment_no`→台账） | `REFERENCE` 判据 + `asset_lineage` |
| **个体 (Individual)** | 一条具体资产（`AST-MFG-2026-0001`） | 资产实例 |
| **公理 / 约束 (Axiom)** | **判据（Checker）** | `standard/compiler.py` 的 8 类 Checker |
| **基数约束 (Cardinality)** | 必填 / 条件必填 | `REQUIRED` / `CONDITIONAL` |
| **值域约束 (ValueRange)** | 数值范围 / 受控词表 | `RANGE` / `ENUM` |
| **不相交 / 互斥** | 禁止取值 | `FORBIDDEN` |
| **函数式属性** | 跨字段一致性 | `CONSISTENCY` |
| **本体对齐 (Alignment)** | **条款溯源**：每条判据回指标准第 N 条 + 原文 | `Finding.source` / `clause_text` |
| **本体演化** | **盲区 → 提案 → 裁决 → 入库** | `asset_blindspots` → `std_propose` → 锚点裁决 |
| **本体验证** | **硬锚点**：85 条机械抽取的真值，判据必须在其上表现正确 | `std_hard_anchors` + `std_audit` |
| **推理机 (Reasoner)** | 判据执行器（无需通用推理机） | `StandardVerifier.verify()` |

## 三、8 类判据 ⇄ 本体约束类型

| 判据类型 | 本体对应 | 实测条数 | 硬锚点覆盖 |
|---|---|---|---|
| 数值范围 `RANGE` | `owl:minInclusive` / `maxInclusive` | 4 | 4/4 |
| 受控词表 `ENUM` | `owl:oneOf` | 5 | 5/5 |
| 格式约束 `PATTERN` | `xsd:pattern` | 4 | 4/4 |
| 必填约束 `REQUIRED` | `owl:minCardinality 1` | 5 | 5/5 |
| 条件必填 `CONDITIONAL` | 带前提的基数约束 | 4 | 4/4 |
| 跨字段一致性 `CONSISTENCY` | 属性间函数依赖 | 5 | **4/5** ← 唯一缺口 |
| 跨文档引用 `REFERENCE` | `owl:ObjectProperty` + 存在性 | 4 | 4/4 |
| 禁止取值 `FORBIDDEN` | `owl:disjointWith` / 黑名单 | 3 | 3/3 |
| **合计** | | **34** | **33/34 = 97.06%** |

> **跨字段一致性 4/5 的缺口**：缺的是"`work_start` ≤ `work_end`"——
> 合规模板里没有这两个字段，抽取器按"**不臆造字段**"原则主动跳过。
> **这是一个正确行为，不是 bug**：宁可缺一条锚点，也不编造一条看起来对的。

## 四、本体的"持续动态更新"是怎么发生的

传统本体的更新是**人工**的。本项目的更新是**被盲区驱动的**：

```
① 资产被人工确认为违规
        ↓
② 现有判据全部放行  ← 这就是"盲区"
        ↓
③ asset_blindspots 报出盲区
        ↓
④ 提炼候选判据（消融实测：必须零误报）
        ↓
⑤ std_propose 提交
        ↓
⑥ 硬锚点裁决：adopted（采纳）/ rejected（驳回 + 理由）
        ↓
⑦ 入库 → 本体长大
        ↓
⑧ 同一批资产再测：盲区 2 → 0   ← 闭环
```

**实测证据**：
- 本地：盲区 `2 → 0`（`evostd.smoke`，可复跑）
- 平台：盲区扫描 **4/4 = 100%**（Nexent 上由 agent 调用 `asset_blindspots` 产出）
- 裁决实测出现 `rejected → adopted → rejected`（第三条因过度宽泛被拒）

## 五、与"标准体系对齐"的实现

**对齐不是口头声明，是数据结构**：

```python
Finding(
    clause_id   = "第36条",                    # ← 回指条款编号
    source      = "《…规范（演示样例）》第36条",   # ← 标准名 + 条款
    clause_text = "数据资产不得引用已停用设备的资产编号。",  # ← 条款原文
    ok          = False,
    message     = "equipment_no 命中了禁止取值：['EQP-1000007']",
    evidence    = {"field": "equipment_no", "hit": ["EQP-1000007"]},
)
```

**每一条判定都同时带着**：条款编号、标准名、**条款原文**、判定理由、证据字段。

所以"与行业规范、标准体系对齐"这件事：
- **对齐对象**：条款原文（不是我的转述）
- **可验证**：拿判定结果去比对标准原文，能逐条核对
- **可审计**：`std_audit` 检查每条判据是否有对应锚点（防止"自造判据"）

## 六、评审可能问的三个问题

**Q1：你的本体会不会只是 if-else 规则，不算本体？**
A：本体与规则引擎的边界在"**是否有类层次与关系**"。本项目有：
- 类层次：资产类型（文本/表格/图文）
- 关系：`source_doc_ids`（资产→文档）、`cited_standards`（资产→标准）、`equipment_no`（资产→台账）
- 约束：8 类公理
- **且比传统本体多一层：可执行 + 可溯源 + 可自演化**

**Q2：知识图谱在哪？**
A：**平台侧无图数据库**（Nexent 依赖白名单限制）。本项目用"条款-判据-资产"三元关系表达图结构，
跨文档多跳由 `multi_hop` 工具承担（资产 → 引用的文档 → 文档里的条款 → 条款约束的其他资产）。

**Q3：半自动化，那另一半呢？**
A：**人只做一件事——确认"这条确实违规"**。
实测：37 条款 → **34 条自动编译（92%）**；85 条硬锚点 **零人工机械抽取**；
人只确认了极少量盲区样本（本地 2 条 / 平台 4 条）。
**其余全部自动化**，且每一环都有机械检验（锚点自检 0 错挂、对抗探针拦病态判据）。

## 七、一句话总结

> **传统本体：人写声明，机器去读。**
> **本项目：机器从标准里长出可执行的判据，人只负责说"这里你漏了"。**
>
> 前者是**知识的表示**，后者是**知识的可用性**。
> 本项目做的是后者的**半自动化构建 + 持续动态更新 + 与标准体系强对齐**。
