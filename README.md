# evostd · 自进化标准合规校验

> **把行业标准条款编译成可执行判据，再用「从标准原文机械抽出的硬锚点」作为外部真值，
> 约束判据库自己的进化。**

---

## 一句话

这个项目对「自进化」给了一个比"AI 自己改自己"更窄、但**可证伪**的定义：

> **自进化 = 系统扩大它"能够分辨的对错"的范围。**
> **而最终裁决者，永远在系统外面。**

所以仓库里最值钱的不是判据，是**一整套"我怎么知道自己没在骗自己"的机械检查**。

---

## 为什么需要这个

主流做法是让模型自我批判、自我打分（Self-Refine / Self-Rewarding）。
问题很直接：**打分的人和被打分的人是同一个，你无法证明它越改越好。**

本项目换了个切法 ——

1. 把标准条款**编译**成确定性判据（不靠模型）
2. 从条款原文**机械抽取**"确定对 / 确定错"的样本（硬锚点，零人工）
3. 新判据**必须通过四道闸门**才能入库：

| 闸门 | 要求 |
|---|---|
| **R1 见过合规锚点** | 判据必须在真实合规样本上跑过 |
| **R2 零误报** | 在合规锚点上不得误伤 |
| **R3 可归因命中** | 必须抓到现有判据抓不到的违规，且指得出是谁 |
| **R4 严格度不劣化** | 不得比标准原文更松 |

4. 系统可以**提议**任何东西，但**裁决发生在它够不着的地方**

## 一个具体例子

标准原文：**"设备检修周期应为 1 至 365 天"**

系统做三件事：

1. **编译** → `1 ≤ maintenance_cycle_days ≤ 365`
2. **生成考题**（从原文机械抽取，零人工）：90 天应通过 / 0 天应报错 / 366 天应报错
3. **一条资产填 400 天** → 输出：

> 违反**第5条**，原文："设备数据资产登记的检修周期应为 1 至 365 个自然日之间的整数。"

**每条判定都能追回标准原文** —— 这是"可溯源"的实质。

再看一个更关键的：A 类设备的检修周期上限是 **90 天**（不是 365）。
一条资产**所有格式、枚举、必填字段全对**，只填了 365 天（A 类超限）。

早期版本**抓不到它** —— 因为没有"按类别查上限"这类判据。
这种资产叫**盲区**，它逼着判据语言从 8 类扩张到 12 类（新增"查表区间"），才被抓住。

> **这就是"扩大可分辨范围"的具体含义：不是把尺子改严，是量到以前量不到的地方。**

## 已知限制（如实记录）

| 限制 | 说明 |
|---|---|
| **演示数据** | 标准与资产都是演示编写的。`tools/ingest_standard.py` 已备好，但**从未用真实标准跑过** |
| **检索侧未接** | 本机部署未启用模型引擎（`MODEL_ENGINE_ENABLED=false`），无法生成 embedding；检索走代码内词法匹配。**推理侧完整可测** |
| **语言完备性未证** | 12 类判据均有条款在用，但"该有的都有"从未被证明 |
| **进化回路是超参搜索** | 候选池只有 `-exact/-wide/-tight` 三个变体，能挑一个，**不会提出新的判据类别** |
| **性能** | 1000 条资产 ≈ 20~50 秒（**依负载与机器负载波动，数字不稳定**） |

## 三条贯穿全仓库的纪律

1. **弃权必须可见** —— 判据"判不了"时要明确弃权，不能返回"通过"。
   `std_verify` 的 `abstained` 字段就是为此存在。
2. **改标准是权威行为，不是工程行为** —— 系统只提议修订，不自己改。
   真矛盾（如第7条 1~720 vs 第46条 A类≤24）挂着等人裁决。
3. **修了必须跑一次"应该被拒"的样例** —— 仓库里有多次"以为改了其实没改"的记录，
   全部写在 `docs/42` 里。
