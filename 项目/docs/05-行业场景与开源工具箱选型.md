## 结论先行（TL;DR）

1. **推荐场景：制造（主）+ 政务数据目录（对齐样板）**——理由是**唯一能在两周内同时给出「表格+图文+文本」三模态真实样例、又能给出机器可校验标准锚点**的行业。
2. **推荐流水线**：`PaddleOCR-VL(0.9B) / MinerU2.5(1.2B)` 做多模态解析 → `LangExtract/自研 few-shot` 做本体候选抽取 → `rdflib + pySHACL` 做本体与约束 → `Neo4j(向量+全文索引)` 或 `LightRAG` 做多跳检索 → **PROV-O 溯源图**做证据链。
3. **最关键的工程判断**：**不要用 Docker**（本机没有），全部走 `pip` + 纯 Python 库；**不要用 Kuzu**（项目已归档）；**本体不要"自动学习"**，要"半自动 + 人审 + SHACL 卡口"——这恰好也是赛题原文的"半自动化"。
4. **对齐如何可计算**：把标准条目拆成三类落点——**字段名→SHACL 属性路径**、**编码规则→正则/枚举**、**业务合理性→SHACL-SPARQL 规则**。演示时故意喂一条违规数据，让校验器报出「违反 GB/T XXX 第 N 条」。
5. **两周 MVP 的取舍**：砍掉权重训练、砍掉全自动本体学习、砍掉全量标准编码；只做**一个闭环 + 一条多跳链 + 一次对齐校验 + 一份溯源证据**。

### A.1 明确推荐

> ### 🎯 推荐：**制造（主场景）+ 政务数据目录（对齐样板，只做一小块）**

**为什么是制造**

1. **三模态齐备且低成本**：设备台账/点检表（**表格**）、质检报告附图与缺陷照片（**图文**）、维修工单与故障案例（**文本**）——三类都是工厂里真实存在、且我们能用公开数据集 + 少量自造样例覆盖的。医疗的最强模态（自由文本病历、DICOM 影像）恰好在公开样例里被"阉割"了：MIMIC-IV 演示集官网写明 *"excludes free-text clinical notes"*（[来源](https://physionet.org/content/mimic-iv-demo/2.2/)）。
2. **标准体系是"天然分层"的，画图即说服力**：ISA-95（IEC 62264）本身就定义了企业—控制系统的层级模型，OPC UA（IEC 62541，国标 GB/T 33863.1-2017 采标）定义了信息模型与地址空间。这意味着"标准条目 → 本体类/属性 → SHACL 约束"这条链路**不需要我们编造映射**，标准原文就是分层描述的。
3. **"沉睡数据"叙事最硬**：老设备台账、纸质维修记录、无标注的缺陷照片、老师傅脑子里的经验——**每一类都对应一种多模态能力**，且演示时可以直接说"这个数据以前躺在 Excel 和文件夹里，现在它是一等公民资产"。
4. **风险最低**：不涉及个人隐私与金融监管红线，数据可自造、可公开，评委不会因合规问题扣分。

**为什么不选另外三个**

- **不选医疗**：并非题材不好，而是**证据链最弱**——公开可得的 MIMIC-IV 演示集只有 100 例且**不含自由文本临床笔记**；真正的 MIMIC-IV 与 MIMIC-IV-Note 需要 credentialed 申请（[MIMIC-IV](https://physionet.org/content/mimiciv/3.1/)、[MIMIC-IV-Note](https://physionet.org/content/mimic-iv-note/2.2/)），赛期内拿不到授权就是空转；DICOM 影像链路在两周内属于"高风险低产出"；SNOMED CT 为会员制许可（[官方许可说明](https://www.snomed.org/)），不能作为可分发样例。
- **不选金融**：公开样例（SEC EDGAR、XBRL）**语义对齐对象是美股披露规则**，而我们能讲清楚、能引用的国内标准（JR/T 系列、EAST/1104/一表通报送）**没有配套公开样例**。这会逼出"标准是国内标准、数据是美国数据"的尴尬错位，评委一问就露。⚠️ 另外本机脚本直连 `sec.gov` 返回 403（bot 防护），需改用浏览器或加 UA 头，演示环境有额外不确定性。
- **不选政务做主角（但保留做样板）**：官方文件确实点名了"**目录与实际数据资源'两张皮'**"（[《全国一体化政务大数据体系建设指南》](https://www.gov.cn/zhengce/zhengceku/2022-10/28/content_5722322.htm)），这是极好的问题定义。但纯政务场景**缺"图文"这一模态的天然样例**，需要自造证照扫描件；且数据开放平台的许可逐条不同，两周内做许可核查是纯消耗。**因此：把政务的"目录-数据映射与对齐覆盖率"做成制造场景里的一个小模块（即"给制造数据资产也建目录、也算对齐覆盖率"），既拿到这个叙事，又不背它的包袱。**

**取舍一句话**：用制造拿"多模态 + 标准对齐 + 沉睡资产"三分，用政务目录的"映射覆盖率"做一个可复用的对齐度量组件。

**B.1 结论（推荐组合）**：
- **主力：PaddleOCR-VL（0.9B）** —— 官方明示支持 Windows，0.9B 适配 8GB 显存，表格/图文指标公开可引，Apache-2.0 干净。
- **兜底：docling（MIT）** 负责 Office/PDF 的稳定转换与表格结构；**markitdown** 作为最快降级路径。
- **MinerU 作为"中文复杂版面"的第二意见**，但许可附加条款与后端依赖要在赛期内先验证。
- **明确排除**：DeepSeek-OCR（Windows+vLLM 风险 + 已被 OCR2 取代）、PDF-Extract-Kit（AGPL）。

### B.2 表格理解 / 图表理解

- **表格结构**：优先 `PP-StructureV3`（带单元格坐标，见上 PaddleOCR 仓）与 `docling TableFormer`。
- **图表理解**：PaddleOCR-VL 的 release note 明确写了增强 *chart understanding*（[来源](https://github.com/PaddlePaddle/PaddleOCR)），可复用同一模型，不必再引一个专用模型。
- **表格问答**：本体化之后交给图谱与 LLM（见 B.4），不建议在两周内训练专用 TableQA 模型。

**B.3 结论**：**不要选"全自动本体学习"的重型框架**。推荐组合：
`LangExtract（抽取 + 来源定位）` + `iText2KG 的增量合并思路` + `rdflib/pySHACL（本体与约束）` + `Neo4j 社区版或 LightRAG（检索）`。
理由：这条链**每一环都是纯 Python 或单机可跑**，且**每一环都能直接映射到赛题的一个硬性要求**（抽取→资产标识；增量→动态更新；SHACL→标准对齐；图检索→多跳；来源定位→可溯源）。

### B.4 多跳推理与可溯源

- **混合检索**：Neo4j 官方提供"全文 + 向量 + 图拓扑"三合一的 Cypher 写法（[官方博客](https://neo4j.com/blog/developer/hybrid-search-in-neo4j-full-text-vectors-and-graph-topology-with-cypher/)）；LightRAG 提供 dual-level retrieval 且**支持增量更新与选择性删除**（[README](https://github.com/HKUDS/LightRAG)）——后者对"本体动态更新"这个赛题点更贴。
- **"引用可溯源"的具体做法（可落地）**：
  1. **给每个三元组挂 provenance 四元组**：`(subject, predicate, object, source)`，其中 `source` 指向 `doc_id + page + bbox/cell + span_offset + extractor_version + timestamp`。PaddleOCR 的单元格坐标、LangExtract 的来源定位天然提供这层信息。
  2. **用 W3C PROV-O 表达**：把抽取器建模为 `prov:Activity`、文档为 `prov:Entity`、三元组为 `prov:wasGeneratedBy` 的产物（[PROV-O 规范](https://www.w3.org/TR/prov-o/) ⚠️ 脚本访问被 w3.org 的 bot 防护拦为 403，链接本身为标准页面）。
  3. **证据链最小集**：回答问题时返回的不是"答案+文档列表"，而是**跨文档的最短证据路径**（图上的多跳路径），每跳标注来源——这就是"决策链路可溯源"的可视化形态。
  4. **拒绝无源断言**：设一条硬规则——**没有 provenance 的三元组不允许进入推理**（在图谱查询层用属性存在性约束实现）。这条规则本身就是演示中的亮点。

## C) "与标准体系对齐"如何做到可计算

核心思想：**标准条目不是文档，是约束**。一条标准原文通常只包含三类可计算成分，把每一类落到一个具体的机器可校验位置：

| 标准条目的成分 | 落到哪里 | 例子（以制造为例） |
|---|---|---|
| **字段是否存在 / 类型 / 基数** | **SHACL `sh:property` + `sh:path` + `sh:datatype` + `sh:minCount`** | 「设备资产必须具备唯一编码与所属产线」→ `ex:Device` 上 `ex:deviceId` `sh:minCount 1`、`ex:belongsToLine` `sh:minCount 1` |
| **受控词表 / 编码规则** | **SHACL `sh:in`（枚举）或 `sh:pattern`（正则）**，词表直接来自标准码表 | 「缺陷类型必须取自规定集合」「工单号必须匹配厂内编码规则」→ `sh:in ( "裂纹" "划痕" "夹杂" ... )`、`sh:pattern "^WO-\\d{8}$"` |
| **跨字段 / 跨文档的业务合理性** | **SHACL-SPARQL（`sh:sparql`）或规则引擎** | 「停机超 4 小时的工单必须挂接质检报告」「A 设备的维修动作不能引用 B 设备的照片」→ 一条 SPARQL 约束即可表达 |

**三个可落地模式**

**模式 1：条款 → 受控词表本体（最稳，先做这个）**
把标准里的分类/代码表抽成 SKOS 概念表或 OWL 枚举类，本体属性用 `sh:in` 指向它。
*演示*：质检报告的"缺陷类型"字段值不在码表内 → `pySHACL` 报 `Constraint Component sh:In` 违规，并显示 **"违反 GB/T XXX 第 N.2 条（缺陷分类）"**。用 [xpSHACL](https://ar5iv.labs.arxiv.org/html/2507.08432) 的思路把违规翻译成人话。

**模式 2：目录—数据映射与对齐覆盖率（最像"资产盘点"）**
借鉴政务"目录-数据映射"的做法（官方文件明确要解决"目录与实际数据资源两张皮"，见 [国办函〔2022〕102号](https://www.gov.cn/zhengce/zhengceku/2022-10/28/content_5722322.htm)）：为每类多模态数据资产建一条目录项（名称/来源系统/模态/责任部门/标准数据元/映射字段），**自动计算对齐覆盖率 = 已映射字段数 / 应映射字段数**。
*演示*：一页仪表盘——"设备台账 92% 对齐、质检图文 46% 对齐（缺缺陷类型码）"，点击下钻到具体缺口。**这是评委最容易一眼看懂的"对齐"。**

**模式 3：规则即条款（可解释性最强）**
用 SPARQL 规则或 SHACL-SPARQL 表达"业务合理性"，每条规则**强制带 `dct:source` 指回标准条款 URI**。
*演示*：故意构造一条冲突数据（例：同一设备同一时间出现在两条产线的点检记录），系统报出冲突 + 两条相互矛盾的证据来源 + 触发的标准条款。

**演示中如何体现"对齐"（三幕，共约 3 分钟）**
1. **喂入**：上传一份新质检报告（含缺陷照片）→ 系统自动抽取 → 生成 RDF 三元组，并给每个字段标注它对齐到哪个标准数据元。
2. **卡口**：故意让"缺陷类型"写成码表外的值 → 校验器**拒绝入库**并给出标准条款引用；改正后通过。**这一步证明"对齐"不是口号而是有牙齿的。**
3. **覆盖**：打开对齐覆盖率仪表盘，展示 24 小时内新增资产的映射率变化曲线——**证明"持续动态更新"发生了**。

## D) 两周冲刺的最小可行方案

### D.0 明确"不做"清单（比做什么更重要）

| 不做 | 理由 |
|---|---|
| ❌ 训练/微调任何权重模型 | 8GB 显存 + 14 天 = 只会在演示前一周崩掉 |
| ❌ 全自动本体学习 | 赛题原文就是"**半**自动化"；全自动的效果不可控且难以评测 |
| ❌ 全量行业标准编码库 | 只做**一套标准的一个子集**（例如 GB/T 37413 的术语 + 一条编码规则 + 一条业务规则） |
| ❌ Docker 化部署 | 本机无 Docker；全部走 `pip` + 单机脚本，用 `requirements.txt` 代替镜像 |
| ❌ 图表/视频模态 | 先保住"文本 + 表格 + 图文"三模态，视频是纯加分项且成本高 |
