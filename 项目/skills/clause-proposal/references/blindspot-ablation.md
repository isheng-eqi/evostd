# 盲区实测纪律与消融证据口径

## 一、盲区的定义

**盲区 = 人判违规、但现行判据库全部放行的情形。**

它不是「系统还不懂的东西」，也不是「标准里很含糊的条款」。它有且只有一个判据：

> 拿这批样本跑 `std_verify`，返回 **0 条违例**。

返回 1 条违例，它就不是盲区，现有判据已经覆盖。

## 二、为什么必须实测（三条第一手教训）

| # | 教训 | 后果 |
|---|---|---|
| 1 | **设计者以为的盲区，可能根本不是盲区** | 一次实验里设计者列了 3 类盲区，加入「盲区实测确认」后，其中 1 类样本数为 13，而现有白名单判据早就把它抓住了 → 真盲区只有 2 类 |
| 2 | **判据语言可能不够用** | 用白名单表达「不得使用已废止标准」是不可能的：白名单要求取值在集合内，而这条要求取值不在集合内。回路会卡死在第一代，直到判据语言被扩张出「黑名单」这一类 |
| 3 | **锚点覆盖度就是天花板** | 锚点只暴露了 2 类真盲区，系统就只学会了这 2 类。第 3 类学不到，因为它不是盲区 |

这三条合起来给出一个可操作结论：

> **人的工作量与「盲区数量」成正比，而不是与「标准规模」成正比。**
> 标准从 14 条涨到 140 条，人要确认的样本数几乎不变。

所以不要为了「多提几条判据」而把一个盲区拆成三条。**拆得越多，人工确认成本越高，收益不变。**

## 三、消融证据的最小字段

```json
{
  "BS-001": {
    "assets": ["AST-2026-0031", "AST-2026-0032"],
    "checked_clauses": 12,
    "violations": 0,
    "snapshot_id": "clause-db-2026-10-11T09-00-00Z",
    "judged_by": "人工判读 + asset_blindspots 归集",
    "note": "该批资产人工判为违规，现行 12 条判据全部放行"
  }
}
```

| 字段 | 为什么必须有 |
|---|---|
| `assets` | 证据可复算：换个人拿同一批资产重跑，必须得到同样结论 |
| `checked_clauses` | 说明「放行」是在多少条判据下发生的。判据库为空时的放行毫无意义 |
| `violations` | **必须为 0**。脚本以此判定盲区成立 |
| `snapshot_id` | 判据库会变。没有快照标识的放行证据在判据库更新后失效 |
| `judged_by` | 写清「违规」这个前提是谁给的。**不能是你自己的判断**——判定权不在你手里 |

## 四、常见错误

| 错误 | 为什么错 | 正确做法 |
|---|---|---|
| 「我看这几条资产明显不合规，现有判据没报，所以是盲区」 | 「违规」这个前提是你下的 | 前提必须来自人工判读记录或用户明确指认；你只负责证明「现有判据放行」 |
| 用 `std_verify` 没报错 当作盲区证据 | 「没报错」与「0 违例」不是一回事 | 看返回里 `violations` 是否为 0，或 `results[].compliant` 是否全为 true |
| 拿一条资产证明盲区 | 单条样本可能恰好命中别的判据 | 至少 2 条同类样本，且逐条确认 0 违例 |
| 判据库快照变了还沿用旧证据 | 证据失效 | 重跑实测，刷新 `snapshot_id` |
| 把「未编译条款」当盲区 | 未编译条款是**已知**的无人把关区，不是未知盲区 | 未编译条款走判据语言扩张；盲区走本技能 |

## 五、盲区 → 提案的准入清单

一条盲区要进入 `std_propose`，必须同时满足：

- [ ] 能用「字段 + 取值条件」说清什么算违规（可机械判定）
- [ ] 有 ≥ 2 条同类样本，且实测 `violations == 0`
- [ ] 至少一条硬锚点，或一批「合规样本不被误伤」的反证
- [ ] 涉及的受控清单已在判据库中声明
- [ ] 与现有判据不同类不同字段（否则先解决重复问题）
- [ ] 八类判据语言表达得了；表达不了 → 改提「判据语言扩张」

任何一项不满足，就把候选项留在报告里标注「未准入」并写清缺哪一项。
**不要为了让它过而修改证据。**
